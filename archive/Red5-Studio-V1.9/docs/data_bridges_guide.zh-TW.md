# Data Bridges — Setup Guide for Beginners

A **data bridge** is just a pipe. The controller knows what's happening with your AHUs (supply temp, fan speed, etc.). A bridge sends that information out somewhere else — like a smart-home app, a website, or another building controller.

You don't need to know how the pipe works inside. You just need to fill in **two or three blanks** and flip a switch.

There are four pipes available. Pick the one your other system already uses. If you're not sure, **<!--FROZEN-->Webhook<!--/FROZEN-->** is the easiest.

---

## 1. <!--FROZEN-->HTTP<!--/FROZEN--> <!--FROZEN-->Webhook<!--/FROZEN--> — "<!--FROZEN-->POST<!--/FROZEN--> it to a <!--FROZEN-->URL<!--/FROZEN-->"

**Use when**: You have any system that can receive an <!--FROZEN-->HTTP<!--/FROZEN--> <!--FROZEN-->POST<!--/FROZEN-->. Examples: n8n, Make.com, Grafana Cloud, a simple Python script, your own website.

**What you fill in**:

```json
"webhook": {
  "enabled": true,
  "url": "https://your-website.com/ahu-data",
  "bearer_token": "abc123-secret",
  "publish_interval_s": 30,
  "timeout_s": 5
}
```

**That's it.** Every 30 seconds the controller will <!--FROZEN-->POST<!--/FROZEN--> a <!--FROZEN-->JSON<!--/FROZEN--> blob to your <!--FROZEN-->URL<!--/FROZEN-->. If you set a <!--FROZEN-->`bearer_token`<!--/FROZEN-->, the controller adds a header <!--FROZEN-->`Authorization: Bearer abc123-secret`<!--/FROZEN--> so your server knows it's really us.

**What your server gets**:

```json
{
  "ts": 1739200000,
  "controller": "red5",
  "telemetry": {
    "ahu": {
      "AHU01": {"sa_t": 13.2, "ra_t": 22.4, "oa_t": 8.1, "fan_speed": 65, "band": "B5"}
    }
  }
}
```

**To test it without writing any server code**: use [webhook.site](https:<!--FROZEN-->//webhook.site<!--/FROZEN-->). Paste the <!--FROZEN-->URL<!--/FROZEN--> it gives you into <!--FROZEN-->`webhook.url`<!--/FROZEN-->, click Test Fire, and you'll see the message arrive.

## 2. <!--FROZEN-->MQTT<!--/FROZEN--> — "Talk to my smart-home hub"

**Use when**: You have **Home Assistant**, **Node-<!--FROZEN-->RED<!--/FROZEN-->**, **OpenHAB**, **<!--FROZEN-->EMQX<!--/FROZEN-->**, or any "smart-home" or IoT platform. They all speak <!--FROZEN-->MQTT<!--/FROZEN-->.

**What you fill in**:

```json
"mqtt": {
  "enabled": true,
  "broker_host": "192.168.1.50",
  "broker_port": 1883,
  "tls": false,
  "username": "homeassistant",
  "password": "your-password",
  "topic_prefix": "controller/red5",
  "publish_interval_s": 30,
  "qos": 1,
  "write_allowlist": []
}
```

**Translation in plain English**:
- <!--FROZEN-->`broker_host`<!--/FROZEN--> is the <!--FROZEN-->IP<!--/FROZEN--> address or <!--FROZEN-->DNS<!--/FROZEN--> name of your Home Assistant / Mosquitto / etc.
- <!--FROZEN-->`1883`<!--/FROZEN--> is the standard "no encryption" port. Use <!--FROZEN-->`8883`<!--/FROZEN--> and <!--FROZEN-->`tls: true`<!--/FROZEN--> if your broker has a certificate.
- <!--FROZEN-->`username`<!--/FROZEN--> / <!--FROZEN-->`password`<!--/FROZEN--> are what you'd use to log in to the broker. Leave both empty <!--FROZEN-->`""`<!--/FROZEN--> if your broker doesn't require login.
- <!--FROZEN-->`topic_prefix`<!--/FROZEN--> is just a label — pick anything. The controller will publish to <!--FROZEN-->`<topic_prefix>/telemetry`<!--/FROZEN-->. So in Home Assistant, subscribe to <!--FROZEN-->`controller/red5/telemetry`<!--/FROZEN-->.

**What Home Assistant sees**: same <!--FROZEN-->JSON<!--/FROZEN--> as the <!--FROZEN-->Webhook<!--/FROZEN--> example above, on the <!--FROZEN-->`controller/red5/telemetry`<!--/FROZEN--> topic, every 30 seconds.

**One-time install on the controller**:

```
pip install paho-mqtt
```

If you skip the install, the bridge stays disabled and the <!--FROZEN-->UI<!--/FROZEN--> shows "<!--FROZEN-->LIB<!--/FROZEN--> <!--FROZEN-->MISSING<!--/FROZEN-->" — no harm done.

### Want to send commands <!--FROZEN-->BACK<!--/FROZEN--> to the controller?

By default, <!--FROZEN-->MQTT<!--/FROZEN--> is read-only — no one can push setpoints to your AHUs. To allow remote setpoint changes, add specific <!--FROZEN-->BACnet<!--/FROZEN--> object-IDs to <!--FROZEN-->`write_allowlist`<!--/FROZEN-->:

```json
"write_allowlist": ["AV1", "AV2"]
```

Now if Home Assistant publishes <!--FROZEN-->`22.5`<!--/FROZEN--> to <!--FROZEN-->`controller/red5/write/AV1`<!--/FROZEN-->, the controller writes 22.5°C to <!--FROZEN-->BACnet<!--/FROZEN--> object <!--FROZEN-->AV1<!--/FROZEN-->. Anything NOT in the list is refused. **Empty list = no remote writes possible.**

## 3. <!--FROZEN-->Modbus<!--/FROZEN--> <!--FROZEN-->TCP<!--/FROZEN--> — "Talk to my <!--FROZEN-->BMS<!--/FROZEN--> / <!--FROZEN-->SCADA<!--/FROZEN--> panel"

**Use when**: You have an existing **Building Management System** (Honeywell, Siemens, Tridium Niagara, Schneider, <!--FROZEN-->JCI<!--/FROZEN--> Metasys, etc.) with a <!--FROZEN-->Modbus<!--/FROZEN--> <!--FROZEN-->TCP<!--/FROZEN--> master that's already polling other devices.

**What you fill in**:

```json
"modbus": {
  "enabled": true,
  "host": "0.0.0.0",
  "port": 5020,
  "unit_id": 1
}
```

**That's it.** The controller becomes a <!--FROZEN-->Modbus<!--/FROZEN--> slave. Your <!--FROZEN-->BMS<!--/FROZEN--> polls it like any other <!--FROZEN-->Modbus<!--/FROZEN--> device.

**Configure your <!--FROZEN-->BMS<!--/FROZEN--> to read** (per <!--FROZEN-->AHU<!--/FROZEN-->):

| Register | Meaning | Format |
|---|---|---|
| 0  | Supply Air dry-bulb °C × 10 | signed int16 |
| 1  | Return Air dry-bulb °C × 10 | signed int16 |
| 2  | Outside Air dry-bulb °C × 10 | signed int16 |
| 3  | Supply Air <!--FROZEN-->RH<!--/FROZEN--> % | uint16 (0-100) |
| 4  | Return Air <!--FROZEN-->RH<!--/FROZEN--> % | uint16 (0-100) |
| 5  | Outside Air <!--FROZEN-->RH<!--/FROZEN--> % | uint16 (0-100) |
| 6  | Fan speed % | uint16 (0-100) |
| 7  | <!--FROZEN-->OA<!--/FROZEN--> damper position % | uint16 (0-100) |
| 8  | Heating valve % | uint16 (0-100) |
| 9  | Cooling valve % | uint16 (0-100) |
| 10 | Band number (1-10) | uint16 |
| 11-15 | reserved | — |

For <!--FROZEN-->AHU<!--/FROZEN--> #2, registers 16–31. <!--FROZEN-->AHU<!--/FROZEN--> #3, 32–47. Multiply by 16.

**Why is <!--FROZEN-->`port: 5020`<!--/FROZEN--> instead of the usual 502?** Standard <!--FROZEN-->Modbus<!--/FROZEN--> port (502) requires root privileges. 5020 doesn't, so it works without messing with system permissions. Just set the same <!--FROZEN-->`5020`<!--/FROZEN--> on the <!--FROZEN-->BMS<!--/FROZEN--> side.

**One-time install**:

```
pip install pymodbus
```

**Test Fire** writes the value <!--FROZEN-->`51966`<!--/FROZEN--> (<!--FROZEN-->`0xCAFE`<!--/FROZEN-->) to register **999**. On your <!--FROZEN-->BMS<!--/FROZEN-->, add a one-time read of register 999 and check that you see 51966 — that proves your <!--FROZEN-->BMS<!--/FROZEN--> is talking to the right slave.

## 4. WebSocket — "I'm building a custom dashboard"

**Use when**: You're writing a **custom web app** (React, Vue, plain <!--FROZEN-->JS<!--/FROZEN-->) that wants live updates. WebSockets keep one connection open forever and the controller pushes updates through it.

**What you fill in**:

```json
"websocket": {
  "enabled": true,
  "host": "0.0.0.0",
  "port": 5021,
  "write_allowlist": []
}
```

**Connect from your web app**:

```javascript
const ws = new WebSocket('ws://controller-ip:5021/');
ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);
  console.log('Telemetry update:', msg.telemetry);
  // msg.telemetry.ahu.AHU01.sa_t etc.
};
```

The controller pushes the same <!--FROZEN-->JSON<!--/FROZEN--> blob (see <!--FROZEN-->Webhook<!--/FROZEN--> example) to every connected client every few seconds.

**Want to send commands back?** Same <!--FROZEN-->`write_allowlist`<!--/FROZEN--> rule as <!--FROZEN-->MQTT<!--/FROZEN-->. Then in your web app:

```javascript
ws.send(JSON.stringify({cmd: 'write', object_id: 'AV1', value: 22.5}));
```

**One-time install**:

```
pip install websockets
```

## How to test that it actually works

After you fill in the config and flip the switch <!--FROZEN-->ON<!--/FROZEN-->, click the **Test Fire** button next to that bridge. The controller will immediately fire one message of the right format so you can verify the receiving side parses it correctly — instead of waiting 30 seconds for the next regular publish.

- **<!--FROZEN-->Webhook<!--/FROZEN-->**: posts a <!--FROZEN-->`{"test": true, ...}`<!--/FROZEN--> payload to your <!--FROZEN-->URL<!--/FROZEN-->
- **<!--FROZEN-->MQTT<!--/FROZEN-->**: publishes one message to <!--FROZEN-->`<topic_prefix>/test`<!--/FROZEN-->
- **<!--FROZEN-->Modbus<!--/FROZEN-->**: writes <!--FROZEN-->`0xCAFE`<!--/FROZEN--> (51966) to register 999
- **WebSocket**: broadcasts <!--FROZEN-->`{"hello": "world", "test": true, ...}`<!--/FROZEN--> to connected clients

If Test Fire reports <!--FROZEN-->OK<!--/FROZEN--> and your downstream system receives the message, you're done — flip back to the regular bridge and let the 30-second cycle do its thing.
