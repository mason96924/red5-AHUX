BACnet AHU Data Bridge Strategies

Context and comparison for the unfinished ingestion path: how red5-ahu should gather AHU + associated VAV data from BACnet (and later non-BACnet) controllers.

Focus: inbound data bridge First target: BACnet AHU Canonical output: /api/data

Context

There are one or more AHUs whose data red5-ahu needs. Each AHU has associated VAVs. Each AHU acts as a controller that communicates with its VAVs. An AHU may or may not support a composite payload (JSON, packed CSV string, etc.) that returns all AHU + VAV points in one response.

The first data bridge to finalize is for a BACnet AHU controller. Outbound bridges (MQTT / webhook / Modbus / WebSocket that publish telemetry elsewhere) are a separate concern. This document is about reading field data into red5-ahu.

Design principle

red5-ahu should never speak “vendor BACnet” in the UI layer. It should always consume a canonical AHU + VAV snapshot (the shape GET /api/data already expects). The unfinished piece is the ingestion adapter that fills that snapshot from each AHU.

Intended spine

AHU controller(s)  →  edge collector / adapter  →  telemetry.json  →  /api/data  →  dashboard
                              ↑
                         write-queue (SATSP, OAD, …)

What red5-ahu needs (minimum)

  • AHU: OAT, OAH, SAT, SAH (psy + band logic); optional MAT/MAH, dampers, fan points
  • Per VAV: zone t, rh (plus cfm / damper / setpoints for graphics)
  • RA: often not on AHU CSV — fallback = mean of VAV zone t/rh
  • Writes: sparse setpoints such as SATSP, OAD (band write-back)

Adapter shape (recommended)

                 ┌─────────────────────────────┐
  BACnet CSV ──► │                             │
  BACnet map ──► │  AHU Adapter (normalize)    │──► telemetry /api/data
  JSON/MQTT  ──► │                             │
                 └─────────────────────────────┘

Dashboard and band logic stay adapter-agnostic. Only the edge collector changes when the next AHU cannot pack CSV/JSON.

Practical BACnet constraints

Constraint Implication
MS/TP is slow Prefer A (1 read/AHU) over B (dozens–hundreds of reads).
AHU is master of VAVs Prefer reading through the AHU (A/D), not discovering every VAV as a separate BACnet device unless forced.
RA often isn’t on AHU Keep VAV-averaged zone T/RH as fallback when no RAT/RAH.
Writes are sparse Every adapter needs a clear write path (CSV sparse write vs multi-WriteProperty).
Edge vs cloud BACnet stays on-prem (Red5 controller / sidecar). Cloud polls the edge API, not BACnet directly.

Recommended priority

Prio Action
P0 Finalize Adapter A: BACnet CSV per AHU → canonical telemetry → /api/data (fix path mismatches; soak on real CSV objects).
P1 Define a thin AhuSource interface so A / B / D plug in without touching the dashboard.
P2 Add Adapter B (object map) for BACnet AHUs without composite CSV.
P3 Add Adapter D/E (JSON/MQTT/sidecar) for non-BACnet or multi-vendor later.

Bottom line

For the first BACnet data bridge, stick with composite CSV-per-AHU (A) as the primary method, but architect it as one adapter behind a stable canonical snapshot so you’re not stuck when the next AHU can’t pack JSON/CSV.
